## 1. Overview

MyTodos is a simple, single-user to-do list application. Users can create tasks, edit them, mark them complete, and delete them. The app has no login/authentication — it is intended for a single user's personal task tracking.

**Goal:** Ship a minimal, functional todo app quickly, using React for the frontend and .NET Web API for the backend, with data stored in an in-memory collection (no database).

---

## 2. Scope

### In Scope
- Create a todo item
- Edit a todo item's text
- Mark a todo item as complete / incomplete
- Delete a todo item
- Optional due date on a todo item
- List/view all todos

### Out of Scope
- User accounts, login, authentication, authorization
- Multi-user support / data isolation per user
- Persistent storage (database, file storage) — data resets when the backend restarts
- Priority levels, tags, categories, subtasks, reminders/notifications
- Mobile app / offline support

---

## 3. User Stories

| # | As a user, I want to... | So that... |
|---|---|---|
| 1 | Add a new todo with a title and optional due date | I can track something I need to do |

## 4. Functional Requirements

### 4.1 Todo Item Fields
| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | GUID/int | Yes | Generated by backend |
| `title` | string | Yes | Non-empty text |
| `dueDate` | date | No | Optional |
| `isComplete` | boolean | Yes | Defaults to `false` |
| `createdAt` | datetime | Yes | Generated by backend |

### 4.2 Features
1. **Create Todo** — User enters a title (required) and optional due date, then submits. New todo appears in the list with `isComplete = false`.
2. **Edit Todo** — User can update the title and/or due date of an existing todo.
3. **Complete Todo** — User can toggle a checkbox/button to mark a todo complete or incomplete.
4. **Delete Todo** — User can delete a todo, with a simple confirmation (e.g., browser confirm dialog).
5. **List Todos** — All todos are displayed on page load, showing title, due date (if set), and completion status. Completed todos are visually distinguished (e.g., strikethrough, greyed out).

---

## 5. Technical Requirements

### 5.1 Architecture
- **Frontend:** React (single-page app)
- **Backend:** .NET Web API (ASP.NET Core)
- **Data Store:** In-memory collection (e.g., a static `List<Todo>` or a singleton service) — no database. Data is lost on backend restart.
- **Communication:** Frontend calls backend via REST endpoints (JSON over HTTP)

### 5.2 API Endpoints (Backend)
| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/todos` | Get all todos |
| GET | `/api/todos/{id}` | Get a single todo |
| POST | `/api/todos` | Create a new todo |
| PUT | `/api/todos/{id}` | Update a todo (title, dueDate, isComplete) |
| DELETE | `/api/todos/{id}` | Delete a todo |

### 5.3 Non-Functional Requirements
- App should load and respond to actions in under 1 second (local/dev environment).
- CORS enabled on backend to allow frontend (different port) to call the API during development.
- Basic input validation: title cannot be empty.
- No offline support required; app assumes backend is running and reachable.

---

## 6. Assumptions & Constraints
- Single user, no authentication — anyone with access to the app can view/edit/delete all todos.
- Data is not persisted across backend restarts (in-memory only), per requirement.
- No pagination needed initially — todo list is expected to stay small.
- Runs locally / in a single environment; no deployment/hosting requirements specified.

---

## 7. Success Criteria
- User can perform all CRUD actions (create, edit, complete/incomplete, delete) without errors.
- Todo list correctly reflects state changes immediately after each action.
- No critical bugs in the core create/complete/delete flow.

## 8. Project Structure

### 8.1 Frontend (React) — `mytodos-frontend/`

```
mytodos-frontend/
├── public/
│   ├───index.html
│   └───favicon.ico
├── src/
│   ├───components/
│   │   ├───TodoList.jsx ......... Renders the list of todos
│   │   ├───TodoItem.jsx ......... Single todo row (complete/edit/delete)
│   │   └───TodoForm.jsx ......... Form to add/edit a todo
│   ├───services/
│   │   └───todoApi.js ........... Handles API calls to backend (fetch/axios)
│   ├───App.jsx ................... Root component, holds todo state
│   ├───main.jsx ................... React entry point
│   └───index.css .................. Global styles
├── package.json
└── vite.config.js .................. (or equivalent bundler config)
```

### 8.2 Backend (.NET Web API) — `MyTodos.Api/`

```
MyTodos.Api/
├── Controllers/
│   └───TodosController.cs ........ REST endpoints (GET/POST/PUT/DELETE)
├── Models/
│   └───Todo.cs .................... Todo entity (id, title, dueDate, isComplete, createdAt)
├── Services/
│   ├───ITodoService.cs ............ Interface for todo operations
│   └───TodoService.cs ............. In-memory store + CRUD logic (singleton)
├── Program.cs ....................... App startup, DI registration, CORS config
├── appsettings.json
└── MyTodos.Api.csproj
```

**Notes:**
- `TodoService` holds the in-memory `List<Todo>` and is registered as a **singleton** so data persists for the lifetime of the running app (but resets on restart).
- `Program.cs` configures CORS to allow requests from the React dev server (e.g., `http://localhost:5173`).
- Frontend and backend are separate projects/folders, run independently (e.g., backend on `https://localhost:5001`, frontend on `http://localhost:5173`).
